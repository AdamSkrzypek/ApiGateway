Lista usprawnień do zrobienia w przyszłości w API Gateway.

- **Routing** — dodać jawne trasy dla kolejnych usług i udokumentować publiczny kontrakt endpointów. Obecnie istnieją trasy Order Service, routing przez `lb://order-service` oraz Eureka; nie jest to już routing statyczny.
- **Rate limiter** — dodać `RequestRateLimiter` (wbudowany w Spring Cloud Gateway) + Redis jako backend, żeby ograniczyć liczbę requestów per klient/IP/user.
- **Resilience4j / Circuit Breaker** — owinąć wywołania do downstreamów (Order Service itd.) w Resilience4j circuit breaker, żeby padnięcie jednego serwisu nie zabijało całego Gateway; do przemyślenia też retry i timeout policy obok samego circuit breakera.
- **Service discovery i registration** — Eureka Server działa już w aplikacji Gateway, a trasa Order Service używa `lb://order-service`. Do uzupełnienia pozostaje konfiguracja środowiskowa i docelowa dostępność registry; patrz `api-gateway-plan.md`.
- **Load balancing** — routing używa już filtra Spring Cloud Gateway `lb(...)` dla Order Service. Zweryfikować zachowanie z wieloma instancjami i dodać trasom usługowym tę samą integrację.
- **Distributed messaging** — ocenić, czy i gdzie w architekturze potrzebna jest komunikacja asynchroniczna między serwisami (np. Kafka/RabbitMQ) zamiast/obok synchronicznych wywołań przez Gateway — na razie nie ustalone, wymaga osobnej decyzji architektonicznej.
- **Spring Security** — uzgodnić kontrakt z Auth Service, a następnie skonfigurować OAuth2 Resource Server, reguły dostępu i bezpieczny kontekst tożsamości. Nie zakładać bezwarunkowego zaufania usług do nagłówków przekazanych przez Gateway; szczegóły w `api-gateway-plan.md`.
- **Mierzenie/logowanie requestów** — sprawdzić istniejące metryki Actuator/Micrometer i dodać brakujące wymiary (czas, status, trasa). Własny `OncePerRequestFilter` tylko dla brakującego zachowania; aplikacja używa Gateway Server MVC.
- **Docker-compose do pracy lokalnej z resztą serwisów** — docelowy schemat pracy: jeden serwis (nad którym akurat się pracuje) odpalony lokalnie z hot reloadem (`spring-boot-devtools`), reszta serwisów jako zbudowane obrazy Dockerowe razem z ich zależnościami (Postgres per serwis itd.) w jednym `docker-compose`, połączone wspólną siecią compose. Uwaga: obrazy "reszty" trzeba od czasu do czasu odświeżać (rebuild), żeby nie pracować przeciwko przestarzałej wersji sąsiednich serwisów — do rozważenia prosty skrypt/`make` do przebudowania wszystkich naraz. Sam build obrazu do puszczenia jako krok CI (nie wymaga dodatkowej zależności w `pom.xml` — `spring-boot-maven-plugin` ma wbudowany cel `build-image`).
- **Health checks / liveness & readiness probes** — wystawić `/actuator/health` (Spring Boot Actuator) na Gateway; przydatne już przy docker-compose (`healthcheck` w definicji serwisu, żeby zależne kontenery czekały na gotowość), a docelowo wymagane przez K8s (readiness/liveness probes).
- **API Versioning** — Gateway to naturalne miejsce na routing po wersji API (np. predicate po `/v1/**` vs nagłówku `Accept`/`X-API-Version`), zamiast rozwiązywać to w każdym serwisie osobno; do ustalenia konwencja, jak tylko pojawi się pierwsza breaking change w którymś z serwisów.
- **TLS / terminacja szyfrowania** — Gateway jako brzeg systemu to naturalne miejsce na terminację TLS (certyfikat wystawiony tu, ruch do downstreamów wewnątrz sieci compose/K8s bez szyfrowania albo z mTLS jeśli dojdzie service mesh); na razie lokalnie nieistotne (HTTP), do zaadresowania przed czymkolwiek zbliżonym do produkcji.
- **WebSockets** — jeśli któryś serwis w Shop będzie tego wymagał (np. powiadomienia w czasie rzeczywistym), sprawdzić proxying WS przez Spring Cloud Gateway (routing po `ws://`/`wss://` działa inaczej niż zwykłe HTTP); na razie brak zidentyfikowanej potrzeby.
